# 第二关训练曲折史（第一关 → 第二关）

> 写给后面做视频的人：下面是这个项目**真踩过的坑**，每条都是"现象 → 我当时的误判 → 决定性实验 → 修复"。
> 时间线是真实顺序，数字都是实测，不是估计。

---

## 0. 起点：第一关已经通了，第二关完全不行

第一关 `runs/ppo_v10`：15M 步，**8/8 局稳定通关**，最远 5776 px。
但换到第二关（Round 1-2，水关，全是海和移动云平台）直接崩：模型走两步就死，平均推进只有几百 px。

水关和第一关的本质区别：**地形变成了"会动的平台"**。第一关踩的是地面，第二关要跳到左右漂移的云上，落点差一点就掉海。而 RAM 里**根本没有地形**，只有像素里有——这就是后面所有麻烦的根源。

---

## 1. 观测融合：为什么必须 CNN + RAM 一起喂

- **纯 RAM 失败**：`runs/ppo_ram_only_final` 训 50 万步，平均 871 px 就卡死。因为坑、悬崖、平台在 RAM 里没有任何表达。
- **纯 CNN 也不够**：平台判别、障碍距离需要精确数值，80×86 的糊图给不出。
- **最终方案**：37 维 RAM 向量 + 80×86×2 灰度帧堆叠（256×240 每 3 像素采 1 个）。

**坑 1：融合层用 Tanh，网络"失明"了。**
现象：蜗牛从 210 px 爬到 30 px，策略 logits 只动了 0.001，跟瞎了一样。
实测：`tools/probe_tanh_sat.py` 打出预激活 |x|≈5.8，**98–100% 单元饱和在 ±1**，整个网络退化成一个符号函数。
修复：换成 `LayerNorm + ReLU`。

**坑 2：动作集缺"跳+扔斧"。**
旧动作集里跳和扔斧是分开的，而**空中**才是遭遇敌人的时刻，导致斧头一度完全没用（6 局 0 击杀）。
修复：动作集扩到 10 个，加 `jump+throw` / `right+jump+throw`。

### 那到底喂了什么：69 个具名变量，不是 2 KB 原始内存

> 常见误解："RAM 观测 = 把内存 dump 给网络"。**不是。** NES 主 RAM 其实只有 2 KB（2048 字节），
> 但我们一个原始字节都没喂——先把内存逆向成结构，再手工挑变量、归一化，拼成定长 69 维。

为什么不直接喂 2048 个字节：绝大多数是渲染暂存、音频寄存器、随机数、栈；字节值只是序数
（`$006D = 109` 这个数字本身没有物理意义）；而且每关布局不同，raw RAM 会让网络死记硬背关卡。

**维度构成（第二关版，69 维 = 37 + 32 关卡 one-hot）**

| 分组 | 维数 | 具体是什么 |
|------|------|-----------|
| 玩家 | 8 | 屏幕 x/256、y/256、速度/64、重力/64、体力/16、**有没有斧头(0/1)**、**有没有滑板(0/1)**、A 键标志 |
| 最近 4 个物体 | 16 | 每个 4 个数：`dx`(clip ±2)、`dy`、`速度/64`、`id/255` —— 按 \|dx\| 排序取最近 4 个 |
| 全局 | 4 | (当前命 − 起始命)/4、关卡、通关标志、世界进度/2048 |
| 最近敌人·水果·道具 | 9 | 三类各一组 `dx, dy, 有没有` |
| 关卡 one-hot | 32 | 当前在第几关（8 岛 × 4 轮） |

**地址层是怎么读的**

- 玩家 = 对象槽 0：`$0564`(id)、`$0574/$0584/$0594`(24 位 X)、`$05B4/$05C4`(Y)、`$05A4`(速度)、`$05D4`(重力)。
  原始值是 16.8 定点，必须 `px = raw/256` 转成像素——实测出生 raw `0x5000` = 80 px、地面 y ≈ 152 px，
  跟屏幕像素对得上才算解码正确。
- 静态地址：`$003F` 命、`$0076` 体力、`$006D` 武器、`$006E` 滑板、`$0072` 死亡、`$007A` 通关、`$0037/$0038` 关卡。
- 其余 15 个槽用 stride `0x10` 遍历：id、世界坐标、速度，然后换算成**相对玩家**的 dx/dy。

**三条设计原则（这就是所谓"标识好"）**

1. **只喂相对量，不喂绝对坐标。** 镜头把玩家钉死在屏幕 x≈96，绝对 x 几乎恒定，喂进去是废维度；
   喂 `dx = 物体x − 玩家x` 才有信息。世界进度因此另用 `$0593`（递减 scroll 寄存器，带 256 回绕累计）单独算。
2. **不按槽号排，按距离排序。** 游戏会复用/打乱槽位——同一只蜗牛这帧在槽 3、下帧可能到槽 7。
   按槽号喂等于逼网络先学"槽位身份"这种假知识；按 \|dx\| 排序后，那 16 维永远是"最近的四个东西在哪"。
3. **语义靠分组，不靠 id 数字。** 敌人 / 水果 / 道具各算一个"最近的"，**是我们查表分类之后才喂进去的**，
   不是让网络从 `oid/255` 这个序数里猜。`oid/255` 只是最弱的附带特征，真正的知识在
   "它进了敌人组还是水果组"这个过滤动作本身。

**归一化踩过的坑**：开关量必须是干净的 0/1。滑板原本写成 `skate/255`，值只有 0.0039，
弱到网络根本看不见——等于"有滑板"这件事从来没进入过观测（详见第 7 节）。

**还有一个过滤**：死亡后游戏会永久保留过期槽数据（字段全冻结，但没有任何 active 标志位，
2 KB 全扫也没找到），那些"僵尸槽"里冻着一只假敌人。靠"字段几十帧不变"判定后剔除，
否则 agent 死后一直看得见一只幽灵蜗牛。

**那为什么还要 CNN？** 因为 RAM 里**没有地形**——平台、坑、悬崖只在 PPU 的 tile/显存里，
没有任何地址能读出"前方 40 px 有个坑"。纯 RAM 模型训 50 万步平均只推进 871 px，就是最硬的证据。
而且 58/59 那种移动平台在 RAM 里只有一个坐标点，要判断"跳过去的落点是不是实地"必须看像素。

分工：**RAM 给精确数值（谁在哪、多远、快不快、我有没有斧头），CNN 给地形与外观（坑在哪、那东西长什么样）**，
两条在 LayerNorm 之后拼接。

## 2. 逆向 RAM：每个"常识"都是错的

**坑 3：槽 15 被当成摄像机寄存器，跳过了——结果主蜗牛永远不画框。**
`$0593`（槽 15 的 x 低位）会随镜头递减，看起来就像 scroll 寄存器。
决定性实验：`tools/probe_snailslot.py`，槽 15 的 3 字节解码落在 0..255 时，**99.3%（5782/5823 帧）坐在一只真实蜗牛身上**。
修复：16 个槽全扫。

**坑 4：颜色区分不了"死亡残留精灵"和活敌人。**
残留和活蜗牛共用鲑鱼色 (236,106,100)。碰撞实验（`probe_ghost_vs_enemy.py`）证实残留无害。
后来改成**行为学检测**：死亡后游戏会永久保留过期槽数据（所有字段冻结，但没有任何 active 标志位——2KB 全 RAM 扫描也没找到），于是靠"字段字节几十帧不变"判定僵尸槽（`ram_map.SlotActivityTracker`）。

**坑 5：id 65 每 768 px 规律出现** → 那是检查点招牌，不是障碍物，别当敌人喂给网络。

## 3. 训练速度：以为跑满了，其实 39%

现象：任务管理器 CPU 只有 39%，我以为没跑满。

真相：这是**同步 PPO 的结构性锯齿**——48 个 worker 采样时父进程闲着，父进程学习时 48 个 worker 全闲着。39% ≈ rollout 占比。

解决：benchmark 后把 worker 从 32 加到 **48**（56 核留 8 个给父进程和系统）：
- 8 workers = 359 步/秒
- 32 workers = 991 步/秒
- **48 workers = 1400–1465 步/秒**

8M 步从 2.2 小时压到 **1.6 小时**。

顺带测出来的反直觉结论：这个**小网络用 56 线程做前向比 1 线程慢 2 倍**（2.62 ms vs 1.30 ms），PPO update 慢 5 倍。并行度全部来自多进程，别开 intra-op 线程。

## 4. 关卡跳入：以为 32 关都能去，结果存了个全黑的档

要做多关卡课程学习，得能直接跳进任意一关。
- 关卡索引 = `area × 4 + round`，写 `$0037`/`$0038` 就能 warp（round 写 4 会滚进下一个岛）。
- **坑 6：存档存早了。** 关卡加载后 PPU 会关约 180 帧，画面**全黑**，但游戏逻辑已经在跑、手柄已经有反应。直接存的档，每一局开头都是几十帧纯黑观测（截图看起来像"还在加载"）。
  修复：加 `wait_for_picture()`，等 `frame.mean() > 30` 再存。
- **坑 7：`np.asarray(nes.step())` 是视图。** 模拟器对象销毁后再读，读到的是垃圾内存，我一度以为两次加载差异 48%。快照处加 `.copy()` 后真实差异 **0.19%**。
- 结果：`saves/stages/` 下 32 个起点存档 + 截图全部可用。

**坑 8：判断"玩家可控"用了假阳性判据。**
通关横幅期间游戏会自己带着人往右走，所以"按 RIGHT 位移 > 5px"会误判。
修复：双条件——**先空闲 30 帧确认不动**，再按 RIGHT 确认能移动。

## 5. 聚类 32 关：连错两次判据

想搞清楚 32 关里到底有几种不同的关卡，错了两回：

1. **按第一帧像素 diff** → 17 种。错，那只看出生屏。
2. **按屏幕坐标** → 21 种。错，镜头把玩家钉死在 x≈96，屏幕坐标几乎不动。
3. **按 CameraTracker 的世界推进** → **30 种**。

结论：8-4 全是同一个 BOSS 图（1-4 = 2-4 = … = 8-4），另外还有 1-1 = 4-1 之类的重复地形组。

|----|-----------|-----------|------|

| 59 | DECO（装饰） | **可站立的移动云平台** | 你截图确认玩家站在上面；实测从 x=320 生成、向左漂移、y 固定在 136/152/168 三层 |

| 2 | "扣体力"障碍 | **篝火，碰到直接掉命** | `probe_id4.py`：vx=0、dy=+7（和玩家同在地面线）、接触致死 |

**最重要的那条**：35/37/41 之前**不在 ENEMY_IDS 里**，意味着策略在水关**完全看不见最主要的敌人**——没有"最近敌人"特征、没有投掷目标。这是第二关训练最实质的一次修正。

**教训（也是回答"要不要教 agent 所有 id"的结论）**：
- overlay 上的名字是**给人看的**，网络根本看不到"名字"这一维，它只拿到 `oid/255` 这种裸编号；
- 真正影响训练的只有**功能归组**（进不进 ENEMY_IDS / LETHAL / OBSTACLE），那才决定奖励和碰撞逻辑；
- 外观区分交给 CNN 从像素里学。所以改标签是为了我们自己看得舒服，改归组才是改 agent 的知识。

## 7. 滑板：一个真 bug + 一条被埋没的知识

你提出"滑板 = 多一条命，除非悬崖"，查下来**基本不知道**，而且有个真 bug。

- **真 bug**：obs 里是 `skate / 255.0`，而 `$006E` 只取 0/1 → 特征值只有 0.0 / 0.0039，**信号弱到网络根本看不见**。
  修复：改成 `float(skate > 0)`（干净的 0/1）。
- **实测**（`tools/probe_skateboard.py`）：强制保持滑板=1 时撞同一个敌人不死；**掉海照样死**（无滑板 f238 死，有滑板 f177 死——有板跑得更快所以更早掉下去）。你说的"除非悬崖"是对的。
- **补奖励** `SKATE_SAVE = +2.0`：滑板消失但人没死 = 板替你挡了一击。之前只有"拿到滑板"的奖励，agent 只看得到板"出现"，学不到它是干嘛的。
- **坑 9**：info 字典在 `self._last_skate = skate` **之后**构造，用 `self._last_skate` 比较恒为假。必须在奖励计算处先把布尔量捕获下来。

## 8. 第二关 8M 训练：跑完了，但评估脚本骗了我两次

`runs/ppo_12`：8,005,632 步 / **124.5 分钟** / 48 workers / `--stages "1-2:0.7,1-1:0.3"`。

曲线：每局推进 167 px → ~5400 px；但**后 4M 步只从 4663 涨到 5484**，边际收益明显递减；熵 0.83 → 0.72（策略还挺软）。

**坑 10（大坑）：评估脚本测出来"230 px 就死"，我以为模型废了。**
用 `evaluate.py` 测，20 局全部 307 px / 514 帧死亡，一模一样。拿原生 env 一测，平均 **5961 px**、12 局 8 局跑到 6500+ px。差了 20 倍。

逐项 A/B 后定位到两个播放端错配：

| 错配 | 训练端 | 播放端（旧） | 影响 |
|------|--------|-------------|------|
| **开局斧头** | `env.reset()` 写 `WEAPON=1`（`start_with_axe` 默认开） | 直接从存档开局，没写 | **5961 px vs 308 px** |
| **帧栈间隔** | `env.step()` 跑 4 帧只 push 最后 1 帧 → 两帧间隔 4 帧 | 每帧都 push → 间隔 1 帧 | 观测分布不同 |

模型对"手里有没有斧头"这个特征**完全不鲁棒**——没斧头时每局都在 230 px 那个点死。
（`visualize.py` 一直是对的，所以窗口里看到的才是真的；坑在 `evaluate.py` 和 `enjoy.py`。）

**坑 11：one-hot 关卡位错乱。**
`--stages "1-2:0.7,1-1:0.3"` 的 pool 按**命令行顺序**排，所以 1-2 = 索引 **0**、1-1 = 索引 1；
但 `visualize.py` 按文件名推成"1-2 = 索引 1"。窗口一直在给网络喂错的那一位（实测差 15%：5036 vs 5961 px）。
修复：`train.py` 里 pool 改成按关卡号排序，索引恒等于 `area×4 + round`。
**注意**：`ppo_12` 这个检查点是用旧顺序训的，回放它必须显式 `--stage-idx 0`。

**修好后的真实成绩（1-2）**：

| 测法 | 平均推进 | 通关 |
|------|---------|------|
| 原生 env（`tools/eval_native.py`） | 5961 px | 12 局 8 局到 6500+ px |
| 修好的 `evaluate.py` | 5134 px | **12 局 4 局真正通关**（关卡全长 ~6800 px） |

没过的那 8 局大多死在 **5186 px**——终点前最后一处，差一点点。

**教训**：评估/播放脚本和训练 env 有任何一点不一致，都会让"模型很烂"看起来像真的。现在有了 `tools/eval_native.py`（直接跑原生 env），两边对不上时以它为准。

## 9. 录制通关视频：cynes 不出声

cynes 的 APU 只计时不发声，所以"带原声"的通关视频必须另想办法。

方案：把手柄输入**从上电开始逐帧记录**（title 300 帧 + 按 START 的 90 帧里每帧往 `$0038` 写关卡号做 warp + 探测帧 + 淡入等待帧 + warmup + 整局），再用 **jsnes 回放同一串输入**抓 APU 输出。

新工具：
- `tools/record_clear_2view.py`——同帧输出**两个**视频：玩家视角（带 overlay / 1024×960）+ agent 视角（80×86 灰度 ×8 的马赛克，就是 CNN 真正看到的东西）
- `tools/jsnes_replay2.mjs`——支持 RAM poke 的 jsnes 重放（`$0038` warp 的关键）
- `tools/mux_video.py`——合流

**同步校验**：两侧 dump 的 camera + lives **122/122 完全一致**，jsnes 侧 round=1（确认在 1-2），音频 63.45 s vs 视频 63.4 s。

结果：采样第 2 局通关，5523 px，63.4 秒；greedy 第 1 局死在 **5181 px**（又是那个点）。

## 10. 还没解决的

- **id 41 "两斧才死"** 只有目视证据，模型还没推进到它生成的区段，没拿到数据。
- **重复地形组**（1-1 = 4-1 等）敌人布局是否真的一样，还没逐关比较。
- **5186 px 那个死亡点**到底是什么，还没定位。
- `SKATE_SAVE = +2.0` 有"故意撞敌刷分"的理论风险（每局最多一次，暂保留观察）。
- 后 4M 步边际收益递减，继续堆 1-2 的步数不划算了——下一步要么加 1-3 进课程，要么给平台加 `nearest-platform` 特征（现在 RAM 里完全没有平台坐标，跳云台全靠像素猜）。
