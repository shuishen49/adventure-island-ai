## 第一章 · 1-2（第二关）补遗

### 坑 1：滑板信号弱到网络根本看不见

- **现象**：agent 拿到滑板也不知道用，撞上敌人照样死。
- **误判**：以为是"agent 学不会用道具"。
- **决定性实验**（`tools/probe_skateboard.py`）：强制 `$006E=1` 撞同一个敌人 → 不死；关掉 → f504 死。
  滑板确实吸收一次伤害。但**掉悬崖不救**（1-2 掉海，有滑板 f177 死、没有 f238 死）——
  用户说的"多一条命，除非悬崖"是对的。
- **真因**：obs 里写的是 `skate / 255.0`，值只有 0.0 / 0.0039 → 信号被淹没。
- **修复**：改成 `float(skate > 0)`；另加 `SKATE_SAVE = 2.0`（滑板消失但人没死 = 替你挡了一击）。

### 坑 2：敌人 id 表是残缺的，agent 对一半敌人是"瞎"的

- **现象**：1-2 水关推进不上去，死因说不清。
- **误判**：以为是操作/跳跃学得不好。
- **决定性实验**：用户开观察窗**目视逐个指认** → id 35/37/41 是章鱼家族（41 要两斧才死）、
  59/58 是移动云平台。这些**此前都不在 `ENEMY_IDS`**，等于观测里完全没有它们。
- **修复**：`ENEMY_IDS` 从 `(14,9,4)` 一路扩到 `(14,9,4,35,37,41)`（后面 1-4 又加 7/10/32/56/5）。
- **教训**：**user 的目视指认比我的 RAM 扫描快得多**，有 window 就该让用户看。

### 坑 3：火焰弹"更强"是幻觉

- **现象**：`$006D=2` 是火焰弹，射程 270 px vs 斧头 186 px（+45%），看起来是纯升级。
- **误判**：给火焰弹加了 `FIRE_GAIN=4.0`（比斧头的 3.0 还高），以为稀有且严格更强。
- **决定性实验**（`tools/probe_fire_power.py`，上帝模式 + 全 32 关 3 种子）：
  **斧头在 25 关更远，火焰弹只赢 2 关**，平均差约 −270 px。
- **真因**：场上同时只能有一发弹体。火焰弹单发存活 327 帧 vs 斧头 212 帧（+54%），
  但间歇按 B 时 500 决策内火焰弹只出手 5 次、斧头 8 次（**射速 −37%**）。射程换射速，不是升级。
- **处理**：用户拍板"按之前的来"，保留 `FIRE_GAIN=4.0`（未改）。

### 坑 4：评估端有两条致命错配，让模型看起来"230 px 就死"

这是 1-2 阶段最冤的一条：**模型其实是好的，是评估脚本在骗人**。

1. **开局没预装备斧头**：`env.reset()` 写 `nes[WEAPON]=1`（`start_with_axe` 默认开），
   而 `evaluate.py` / `enjoy.py` 直接从存档开局 → **5961 px vs 308 px** 的差别。
2. **帧栈间隔不一致**：`env.step()` 跑 4 帧只 push 最后 1 帧（间隔 4 帧），
   而 `evaluate.py` 每帧都 push（间隔 1 帧）→ 喂进去的分布和训练时完全不同。

- **修复**：给两个脚本都补上；并且**评估一律改用 `tools/eval_native.py`**（直接用真 env）。
- **连带**：`record_clear_2view.py` 有同一个帧栈 bug，修完同 seed 从 824 px → **5670 px**。

### 坑 5：one-hot 关卡位错乱（差 15% 性能，还极难发现）

- **现象**：窗口里跑 1-2 只有 5036 px，评估却有 5961 px。
- **误判**：以为是随机性/采样差异。
- **真因**：`--stages "1-2:0.7,1-1:0.3"` 的池按**命令行顺序**（1-2=idx0、1-1=idx1），
  而 `visualize.py` 按**文件名猜**（1-2=idx1）→ one-hot 喂错。
- **修复**：`train.py` 改成池按关卡号排序（`1-1,1-2,...8-4`），杜绝以后再错。

### 坑 6：训练速度估错 7.5 倍

plan.md 估 2700 步/秒，实测 8 workers = 359 步/秒、32 workers = 1024、48 workers = 1400~1465。
（机器是 2×Xeon 8176，56 核 112 线程。）8M 步 ≈ 1.6~2 小时。
另外 **CPU 39% 不是没跑满**：同步 PPO 的 rollout/learn 锯齿，属正常。

## 第二章 · 1-3（第三关）

### 坑 7：greedy 在爬墙段陷入确定性死循环

- **现象**：用户截图 STA 0、ACT=right、贴着蓝砖墙不动。`tools/diag_stall.py` 8 局里 **4/8 卡死在 2851~3073 px**。
- **误判**：体力耗到 0 是"饿死"→ 加了饥饿相关怀疑。实际是卡太久的**果**不是**因**。
- **决定性实验**：上帝模式脚本机器人（每步清零 `$0072`）"每 1.7 秒跳一次"的蛮跳**能过墙并走到 6886 px**
  → 路是通的，纯策略问题。
- **重要认知**：`visualize.py` 是 **greedy(argmax)**，确定性策略在死循环段会永远卡住；
  训练用随机采样能探索出去。**看窗口卡住 ≠ 训练学不会。**

### 坑 8：`--init-from` 继承步数，导致"秒退"

- **现象**：从 8M 检查点热启动却给 `--timesteps 8000000` → **0.0 分钟"完成"直接退出**。
- **真因**：`train.py` 的 `total_steps` 从 checkpoint 里的 `steps` 起算。
- **修复**：目标 = 已有步数 + 想再训的步数（例：8M + 8M = 16000000）。**这个坑后来又踩了一次。**

### 坑 9：`nes.save()` 不是裸 RAM —— 一整批探针结论作废

- **现象**：扫 RAM 找 id199 相关字节，v1/v4/v5 三个版本各给出一个"答案"，互相矛盾。
- **真因**：`nes.save()` 是 **5382 字节的存档 blob**（模拟器状态头 + RAM + PPU + APU），
  我拿 blob 偏移当 RAM 地址用 → 扫出来的全部作废。
- **修复**：读真 RAM 必须 `nes[i]` 逐字节，或先标定 blob 内 RAM 的偏移。

### 坑 10：id199"吃不掉"，最后实锤它是无敌状态的伴生白雾

- 全 32 关只有 1-3 出现。瞬移到它身上 / 按住跳 / 连续挥斧**都吃不掉**，分数命数体力全不变。
- **决定性实验**（`tools/probe_fairy_inv.py`）：199 在场时把敌人钉到玩家身上 → 死亡标志 = 0（2/2）；
  199 不在时同样操作 → = 1（2/2）。**"槽位出现 199" == 无敌状态**，RAM 里没有计时器字节。
- 顺带：`INV_GAIN=3.0` 上升沿奖励 + obs 71 维（末尾加 invincible 位）。

### 坑 11："1-3 全长 6900 px"是假信号

- `tools/probe_13_length.py` 用上帝模式（每步清零 `$0072`）跑出 STAGE_COMPLETE 在
  5074 / 6119 / 5331 / 5847 px —— **四个 seed 四个答案**。
- **真因**：上帝模式下玩家卡在死亡动画里，状态错乱导致的假阳性。
- 真实通关点 6536~6804 px（模型实测 CLEAR 那局的 max progress）。

### 坑 12 ★：1-3 其实早通关了，是"评估起点"选错了

- **现象**：12 局 0 通关，最好 6607 px，学习曲线已平台 → 判定"1-3 未攻克"。
- **误判**：以为模型不行。
- **决定性实验**：改 `--start-round 2`（boot 起点）测 → **16 局 2 局 CLEAR**（ep2 6536 px、ep8 6804 px）。
  之前一直用 `saves/stages/stage_1-3.state` 起点，那个起点和训练时的分布对不上。
- **修复**：**以后评估默认用 `--start-round`，别用 `--start-state`**（除非刻意在某快照上练）。
- 配套：`evaluate.py` 已不可信（obs shim 没跟上 71 维扩维），一律用 `eval_native.py`；
  `eval_native.py` 加 `*** CLEAR ***` 标记（原来只报 x_progress，看不出有没有真的过关）。

### 坑 13：1-2 遗留模型迁移，维度对了但 one-hot 位要重映射

`tools/make_13_init.py` 把 69 维迁到 70 维时，旧的 CLI 顺序是 idx0=1-2 / idx1=1-1，
新排序是 idx0=1-1 / idx1=1-2 → 必须**重写 one-hot 列**，否则策略"看错关卡"。
验证手法：迁移前后在同一局上比 logits（max|diff| ~1e-7 = 等价）。

## 第三章 · 1-4 赶路段

### 坑 14：boss 侦察初期全错，一度以为"1-4 没有 boss"

- **现象**：脚本机器人 696 px 就死，死 49 次；上帝模式卡在 2591 px 以为"镜头锁死"。
- **误判**：先是"1-4 没有 boss"，后是"2591 px 处是 boss 竞技场"。
- **真因**：上帝模式下玩家死亡后**卡在死亡动画**里，镜头当然不动。
- **修复**：`tools/recon_14.py`（模型驱动 + 每帧清零 `$0072`）才走到 3592 px 看到 boss 血条。
- 注：**1-4 必须打死 boss 才过关**（用户确认），不是跑到旗子。

### 坑 15 ★★：度量本身在骗人 —— `x_progress` 可以被"前后震荡"刷分

- **现象**：报告 1-4 平均 1911 px，但看画面明显没走那么远。
- **真因**：`progress() = travel + (x_lo - sx0)` 是**累加口径**。1-4 里 progress 在 ~553 ↔ ~464 反复震荡
  （−89 px 大跳被 `|dp|>=64` 的规则排除不罚，向前爬回的每一步都给正奖励）
  → **原地震荡就能刷分**，一命内震荡 13 次，虚高约 2.4 倍（报 1911 px，实际最远 744 px）。
- **修复**：`progress_r` 改为**只对"新最远点"付钱**，后退按像素照罚；`info["x_progress"]` 直接等于 `best_progress`。
  修完两套口径数字完全一致（漏洞确认堵死）。
- **教训**：**先怀疑度量，再怀疑模型。** 1-3 只虚高 1.17 倍所以没暴露，1-4 就翻车了。

### 坑 16：KILL_GAIN"从来没触发过"是错的（探针 bug）

- **现象**：两个探针都显示击杀恒为 0 → 我一度以为杀敌检测器坏了。
- **真因**：① `kill_dbg` 把"上帧末 / 本帧初"当成两帧比较（其实是同一时刻）→ vanish 恒 0；
  ② eval 打印的是**最后一帧瞬时值**，不是累计。
- **决定性实验**：累计口径重测 → 8 局共 27 杀（3.4/局），检测器一直是好的。
- **教训**：任何"某奖励从未触发"的结论**必须用累计口径验证**，且探针的 prev/cur 时序要和 `env.step` 严格对齐。

### 坑 17：1-4 的敌人 id 几乎全缺

用户目视补：7=青蛙、10=乌鸦、32=从背后冲来的、56=上下移动的蜘蛛；后来又挖出末段的 id5。
这些**全都不在 `ENEMY_IDS`**，等于 agent 对 1-4 一半的威胁是瞎的。
死亡热点实测在 1600~2000 px（森林红鸟）和 3336~3395 px（蜘蛛）。

### 坑 18 ★："1-4 长 25000 px"是作弊注入造成的假象

- **现象**：注入 id199（小精灵）或每帧补 `LIVES=9` 后，1-4 跑到 25000~38000 px 永不通关。
- **决定性实验**：同样注入跑 **1-1 / 1-2**（已知能通关的关），也分别跑到 28944 / 28673 px 且不通关
  → **注入破坏了游戏自身的关卡结束逻辑**。
- **根因**：死亡→重生会让相机**向后跳约 1000 px**，而 `CameraTracker` 用 8 位寄存器 `(prev-cam)%256`
  只能记成往前 24 px，于是重跑同一段被算成新进度（每死一次虚涨约 1000 px）。
- **好消息**：`env.py` 里 `dying = DEATH!=0 and STAGE_COMPLETE==0`，第一次死亡就 done
  → **env 本身是干净的**，训练/评估里的 `best_progress` 可信。
- **教训（第 4 次同类）**：**任何"作弊/注入"都必须先在已知能通关的关卡上验证它是安全的**，
  否则得到的"关卡长度/尽头"全是假象。

### 坑 19：防遗忘失败 —— 1-3 被 1-4 的训练拖垮

混合池里 1-3 权重 0.25 不够：1-3 从原模型的 5656/6665（有通关）
→ 14b 的 4351/5589 → 14c 的 2752/3106（0 通关）。
后来 2-1 那轮学乖了：**池里留 ~50% 权重给已通关的关**，实测 1-4 仍是 7/12，没退化。

### 坑 20：权重 ≠ 步数占比

boss 练习关一局只 ~100 步，而完整 1-4 一局几百步。所以想让 boss 战拿到大约一半的样本，
权重得给到 **0.8**（不是 0.5）。改完 boss 命中从"1.7M 步 71 次"变成"0.24M 步 460 次"，约 100 倍。

## 第四章 · 1-4 的 boss（最大的一章）

### 坑 21 ★★★：`$0011` 三次被当成 boss 血量，两次被推翻

这是本项目**单条最反复**的坑：

| 轮次 | 结论 | 怎么被推翻的 |
|------|------|-------------|
| 10-17 深夜 | "像 HP，未验证" | poke 0..14 时血条恒定 11 格；poke 0 也不会让 boss 死 → **排除** |
| 10-18 13:00 | "就是 HP！" 全程恒 8、战斗内单调下降 8→2 | 加了 `BOSS_HIT_GAIN=6.0` |
| 10-18 14:20 | **是倒计时器** | 决定性实验：同一快照下"站着不动" vs "狂扔斧头"得到**逐帧完全相同**的序列 7→6→5→…→0 → 与伤害无关。**增益置 0** |

后续又发现：满血存档=8、扔过斧头=7、bossface=6，看着极像血量；
但**杀了 boss 的 3308 帧全程它恒为 6**。→ `$0011` 永远别付费。

**教训（最重要的一条）**：任何"某字节 = X"的结论，必须做**同快照对照实验**（动 vs 不动）才能判定因果。
相关性（单调下降）骗了我们两次。

### 坑 22：HUD 顶部的"11 格红块"不是血条

从 f=0 就是 11 格且恒定（是**常驻 HUD**）。旧探针把它当 boss 血条是错的。
→ **先测基线**（元素从第一帧就有 = 不是动态血条）。

### 坑 23：boss 是两个 slot 拼成的，打身体没用

- 用户目视确认：**id198 = 头**（浮在上半部）、**id67 = 身体**（下面的大个子），两槽拼一个 boss。
- 用户手动实测：**打身体无效，打头有效** —— 这是找到 HP 字节的关键线索。
- 被击败时 body id 67 → **63**。

### 坑 24 ★：真 HP 信号是 `$0672`（头槽的命中计数器）

- 物体表是**字段优先布局**：id 在 `0x564 + s`，每个字段块间隔 `0x10`，16 个槽。
- **命中计数 = `0x0664 + 头所在槽`**，头在 slot14 时即 **`$0672`**。每命中一次 +1，**0 → 8**。
- 到 8 时：body `67→63`、头 y 从 93 一路升到 5 飞出屏幕、`$007A`(STAGE_COMPLETE) 置 1。
  **8 次正好等于攻略值（第一关 boss 8 击）**。

### 坑 25：几何决定打法 —— 必须"助跑跳 + 空中投掷"

- 头 y=93 / 身体 y=133（y 是底边）。
- **站立扔斧头最高 y=136**（打不到）、**原地跳扔 y=107（差 14 px）** → 只有助跑跳才够高。
- 斧头射程约 57 px，而**贴身（dx<20）接触即死** → 有效窗口 **dx ≈ 25~70**（实测 dx=91/95 稳杀）。
- **A/B 铁证**（`tools/boss_fight_bot.py`）：跳+投 → f3308 通关；只投 ✗；只跳 ✗；都不 ✗。
- 战斗场地**不耗体力**（整场 stamina 恒 10），没有饥饿时间压力，只需别贴身。

### 坑 26：boss 在场时不能为"往前走"付钱

用户要求：血条消失/人物往前走就不该给进度奖励，否则它会直接撞进 boss 怀里送死。
→ `env` 里 boss 在场时 `progress_r` 强行归零（`best_progress` 仍照常更新，度量保持诚实）。

### 坑 27 ★：1-4 一直不通关的真凶 —— boss 一出现就被 stall 砍掉

- **现象**：14h 模型完整 1-4 平均已到 5379 px（几乎 = boss 场地 5400 px），但**0 命中**；
  6 局里 5 局在"到达 boss 那一帧"立刻 `stalled=True` 结束。
- **真因**：`_boss_act_step` 只在"带内投掷 / 命中"时更新，而 boss 是**第 1216 步才出现**
  → 首帧 `idle = 1216 - 0 >= BOSS_STALL_STEPS(600)` → 立刻判停滞，**还扣 1.0**。
  **等于训练一直在惩罚"走到 boss"。**（boss 快照不受影响，因为 boss 从第 0 步就在。）
- **修复**：新增 `_prev_boss_fight`，在 boss 到达那一帧把 `_boss_act_step = self._steps`。
  修完同一模型到达后能活 20~25 步（之前 0 步）。

### 坑 28：策略学会"停在 boss 触发点前不动"

- **现象**：14i 完整 1-4 六局全部走到 cam=222 后**站着 noop 250 步被 stall 结束**，boss 根本不出现。
- **量到的事实**：脚本化"右+跳"从同一帧出发 **145 帧就把 cam 222→231 并触发 boss**
  → boss 触发点 = **cam≈231**，策略停在 222。
- **原因**：stall bug 期间"到达 boss"每局都被 −1.0，策略宁可站着（−1/250 步）也不过去（死亡 −5）。
- **修复**：`BOSS_ARRIVE_GAIN=2.0`（每局只发一次，刷不了）。
- **可复用的诊断手法**：把卡住帧 `nes.save()` 存盘 → 让脚本化 bot 从该帧起跑。
  跑得通 = 策略不想走；跑不通 = 地形/技能问题。

### 坑 29：起始距离决定 boss 战胜负（缺"刹车"）

同一模型：`1-4boss`(dx=91) 命中 [8,8,7,8,7,7,8,8,8,8] 稳杀；
`1-4gate`(dx=120) 命中 [8,0,3,0,0,2] 只有 1/6 杀；真实到达 dx≈131 更差。
`BOSS_APPROACH_GAIN` 只奖励逼近到 72 px，进了带内就没有"待在带里"的理由 → 惯性冲进 boss 怀里。

- 修复 1：`stage_1-4gate.state` 重生成到 **dx=95**（与已掌握的距离一致）。
- 修复 2：`BOSS_HOLD_GAIN=0.03/步`（dx∈(24,72) 持续给分）+ `BOSS_CLOSE_PENALTY=-0.05`（dx<24）
  → **"太近罚、带内奖"的夹逼**，在致命接触前就给信号（死亡 −5 来得太晚，无法塑形）。

### 坑 30：one-hot 索引口径混乱（观察窗从 1-1 开机）

- **现象**：用户说"观察窗是从 1-1 开始的，肯定不对"。
- **真因**：`visualize.py` 只认 `--start-state/--start-round`，`--start-round` 默认 0 → 每次从 1-1 开机；
  而给的 `--stage-idx 4` 只改了 one-hot，**画面和观测完全对不上**。
- **第二个坑**：`--stage-idx` 的语义在"有课程池"和"没课程池"时不同。
  训练里用的是**池下标**（不是 canonical 的 `(area-1)*4+round`）。
- **修复**：`visualize.py` 新增 `--stages`（与 `train.py` 同一解析 + 同一排序）；
  one-hot 用池下标；新增 `env.parse_stage_pool()` **统一给 train / visualize / eval_boss 用**，禁止各自解析。

### 坑 31：伪关卡命名（用户纠正）

我把练习快照命名成 1-5 / 1-6 / 1-7，**看起来像真关卡**。
用户纠正：**游戏只有 32 关（1-1~1-4、2-1~2-4 … 8-4），没有 1-5/1-6/1-7。**
→ 改名 `1-4boss` / `1-4late` / `1-4gate` / `1-4pre` / `1-4approach`；
新增 `env.stage_sort_key()`（先 area、再 round、**再后缀**）；改名时保证**索引不变**，否则已训练策略会错位。

## 第五章 · 最大的坑：假通关（策略把练习快照"背"下来了）

这是 1-4 攻关的最后一个、也是最隐蔽的坑。

### 现象

用户说"不知道为什么又打不过 boss 了，但有可能打到几次头"。查下来：

| 起始帧 | boss 距离 | 命中 | 击杀 |
|--------|----------|------|------|
| `1-4boss`（手工练习快照） | dx≈79 | 7.7/8 | **8/10** |
| `1-4gate`（真实跑过去的到达帧） | dx≈95 | **0** | 0/10 |
| `1-4gate79`（同一帧把人后移到 dx≈82） | dx≈82 | **0** | 0/10 |
| `1-4approach`（430 px 外进场） | — | 0（偶尔 2~5） | 0/10 |

### 两个排除性实验（缺一不可）

1. **不是距离问题**：把 gate 里的人后移到和练习快照一样的 dx≈82 → 仍然 0 命中。
2. **不是 boss 无敌**：脚本 bot（跑跳投，保持 45~75 px）在 `gate79` 上 **262 步内命中 5 次**
   → 那些帧**完全打得动**，是策略自己的问题。

又用 14h / 14j / 14k 的历史 checkpoint 各测一遍 `1-4gate`：**全部 0/10**，存活只有 50~65 步。
→ **从来没有哪个版本能在真实到达帧上打中 boss**。

### 根因

1. 池里只有 `1-4boss` 这一张**固定构图的练习快照**（camera=175、头在屏幕 x=175、固定物体布局）。
   策略把这张图**背下来了**，换个真实构图就不认。
2. **`ENEMY_IDS` 里根本没有 boss（头 198 / 身体 67）** → RAM 特征看不到它，只能靠像素认。
3. `env._warmup()` 在 boss 在场时原来只随机 `noop / jump`，**永远不可能偶然投中**
   → boss 战从头到尾拿不到正样本（冷启动问题）。

### 修复

1. `tools/make_boss_variants.py`：从真实跑动里采样 **8 → 16 个不同构图的战斗帧**
   （camera 64~226、dx 37~130、体力 8~10），全部进池共享 one-hot 3；
   手工快照 `1-4boss` 权重从 0.16 一路降到 0.03，防止继续背图。
2. `_warmup` 改成也会随机 `throw / jump+throw`（不含方向键，不会缩短距离送死）。
3. 新增 `--clear-ends-episode`：打死 boss 立刻结束这一局，让"通关"成为明确的终局信号。

### 结果

- 训练曲线：hits/局 1.35 → **5.24**；kills/局 0.129 → **0.590 → 0.720**。
- 真实到达帧：0 命中 → **5.5 命中、5/10 击杀**（14m）→ `1-4bv1` **10/10 杀**（14n）。
- **完整 1-4 从头：9/12 通关（75%）**。
- **泛化的代价**：手工练习快照上 8/10 → 3/10 杀。**这是预期内的**，
  换来的是所有真实到达帧从 0 变成 5~6/10。**目标指标是真实帧，不是练习快照。**

## 附：反复出现的元教训（下次先读这 7 条）

1. **先怀疑度量，再怀疑模型。** `x_progress` 虚高 2.4 倍、评估起点选错、evaluate.py 的 obs shim 漂移
   —— 三次都是"模型其实没问题，是数字在骗人"。
2. **"某字节 = X"必须做同快照对照实验**（动 vs 不动）。`$0011` 相关性骗了我们两次。
3. **作弊/注入先在已知能通关的关卡（1-1/1-2）验证安全**，否则"关卡长度/尽头"全是假象。
4. **"某奖励从未触发"必须用累计口径验证**，探针的 prev/cur 时序要和 step 对齐。
5. **判断"某状态能不能打"必须用脚本 bot 对照**，否则分不清"状态不可打"和"策略不会打"。
6. **看窗口卡住 ≠ 训练学不会**（窗口是 greedy，会陷入确定性死循环）。
7. **泛化要看真实帧，不要看练习快照**；练习快照分数下降往往是好事。
